# PageSpeed 分數與 AI 引用

# **一、 什麼是代理瀏覽？ (What is Proxy Browsing?)**

# **核心三大支柱**

---

# **1. AI 代理協作**

這是指 AI 從原本被動的「問答角色」，升級為具備主動執行能力的「代理人（Agent）」。

- **技術本質：** 傳統 AI 只能在對話框裡回覆文字。而在代理協作模式下，AI 擁有「眼睛（視覺/DOM 樹解析能力）」與「手（模擬操作接口）」。當你輸入指令，它會自動規劃步驟（如：打開分頁 / 點擊搜尋框 / 輸入關鍵字 / 滾動頁面擷取資料）。
- **實際場景：**日常辦公： 「幫我把這 10 個電商分頁裡的商品名稱和價格抓出來，整理成表格。」自動化填單： 「用我履歷的資料，幫我把這個職缺申請表單填好並送出。」
- **優勢：** 使用者不再需要重複複製貼上，AI 成為你與瀏覽器之間的「高效率過濾層」。

---

# **2. WebMCP 協議（Web Model Context Protocol）**

這是讓 AI 代理能夠順暢運作的底層標準基礎設施。

- **技術本質：** MCP（Model Context Protocol）是由 Anthropic 等 AI 巨頭推動的開放標準，而 WebMCP 則是將其延伸到網頁生態系。它定義了一套標準化的 API，讓「網頁」與「AI 模型」之間能用統一的語言溝通。
- **為什麼需要它？**過去的痛點： 網頁的 HTML 結構混亂、充滿廣告和動態載入，AI 像在看天書，常常「點錯鈕」或「抓錯資料」。
- **WebMCP 的解法：** 網頁端主動提供結構化的資料（Context）與可執行的操作清單（Tools）。AI 只要讀取 WebMCP 接口，就能立刻知道「這個按鈕是結帳」、「這個欄位是地址」，實現百分之百準確的結構化讀取與控制。

---

# **3. 自動化任務與效能穩定性**

當 AI 開始在後頭「瘋狂點擊與擷取」時，瀏覽器與網頁端面臨的效能與架構挑戰。

- **技術本質：** AI 執行任務通常是非同步（Asynchronous）且隱形（Headless）的。為了確保 AI 抓到的資料準確，系統常常需要在背景對網頁進行「快照（Snapshot）」（保存當下的 HTML/DOM 狀態與記憶體數據）。
- **效能穩定性的高要求：**
1. 記憶體與 CPU 暴增： AI 在極短時間內產生的讀取、點擊、快照請求，遠高於人類的操作速度。如果網頁程式碼寫得不好（例如內存洩漏、肥大的 JavaScript），網頁就會直接崩潰（Crash）。
2. 對抗動態渲染： 現代網頁（如 React/Vue）大量使用動態載入。如果網頁效能低落、轉圈圈太久，AI 的快照就會抓到「空白畫面」，導致自動化任務失敗。
3. 防爬蟲機制（Bot Detection）： 高頻率的自動化操作極易觸發網站的安全防護，如何在維持效能的同時，合理區分「惡意爬蟲」與「合法的 AI 代理」，也是這類任務的核心難題。

---

# **二、 關鍵效能目標 (Performance Targets)**

# **目標：200ms 以下的 INP 回應**

為什麼 INP 對代理瀏覽很重要？AI 代理通常會連續觸發多個互動指令。如果 JavaScript 主線程發生阻塞，會導致代理程式超時或執行錯誤。

1. **INP (Interaction to Next Paint)** — 互動到下次渲染延遲指標要求：< 200ms
    
    INP 是 Google 在 2024 年正式取代 FID（First Input Delay）的 Core Web Vitals 核心指標。它衡量的是使用者在網頁的整個生命週期中，進行點擊、輕觸或鍵盤輸入後，瀏覽器需要花多久時間才能把更新後的畫面渲染（Paint）出來。
    
    ### **為什麼重要？**
    
    - **FID 的盲點：** 舊的 FID 只看「第一次」互動，且只計算「瀏覽器開始處理」的延遲，不管畫面有沒有印出來。
    - **INP 的真實性：** INP 看的是「每一次」互動，並且計算完整的 輸入延遲 + 處理時間 + 渲染延遲。只要這三個環節總和超過 200 ms，使用者就會明顯感覺到「網頁慢半拍」。
    
    ---
    
    ### **如何優化？**
    
    - **避免阻塞主線程：** 確保點擊事件觸發的 JavaScript 函式不會執行太久（參考下方的 Long Tasks）。
    - **善用 `requestAnimationFrame`：** 將不影響視覺的非必要邏輯延後執行，優先讓瀏覽器更新畫面。
    - **即時反饋：** 按下按鈕時，立刻加上 Loading 轉圈圈或骨架屏（Skeleton Screen），即使資料還沒好，也能讓 INP 的「下次渲染」提早發生。
    
    ---
    
2. **DOM 節點總數 (DOM Size)**指標要求：< 1400個節點
    
    DOM（Document Object Model）樹是網頁的骨架。Lighthouse 和 Chrome 官方強烈建議，一個網頁的總 DOM 節點數應該控制在 1400 個以內（最大深度不超過 32 層，單一父節點子節點不超過 60 個）。
    
    ### **為什麼重要？-- DOM 節點過多（俗稱 DOM 臃腫）會引發效能雪崩：**
    
    - **記憶體飆升：** 每個 DOM 節點都需要佔用瀏覽器記憶體。
    - **計算代價高昂（Reflow / Re-layout）：** 當 CSS 改變或 JavaScript 動態修改網頁時，瀏覽器必須重新計算整個 DOM 樹的幾何位置。節點越多，計算時間呈指數級增長。
    - **AI 代理的噩夢：** AI 在解析網頁時需要閱讀 DOM 樹，如果節點破萬，會導致 AI Token 消耗暴增、解析速度變慢，甚至無法正確定位按鈕。
    
    ### **如何優化？**
    
    - **虛擬列表（Virtual Scrolling / Windowing）：** 如果有成千上萬筆資料（如電商商品列表、動態牆），只渲染畫面上看得到的節點，滾動時再動態替換內容，不要一次生成幾萬個<div>。
    - **清理無效包裝：** 減少過度巢狀的 `<div><div><div>...</div></div></div>`，善用 CSS Flexbox 或 Grid 來簡化結構善用 CSS Flexbox 或 Grid 來簡化結構。
    - **延遲載入（Lazy Loading）：** 畫面下方的元件（如 Footer、彈窗內容），等到需要時再動態插入 DOM 中。
    
    ---
    
3. **INP (Interaction to Next Paint)** 減少 Long Tasks (長任務)指標要求：減少超過 50 ms的任務
    
    瀏覽器的 JavaScript 是單線程（Single Thread）運行的。所有的 JavaScript 執行、頁面佈局、螢幕渲染都在同一個主線程（Main Thread）上排隊。
    
    **定義： 任何在主線程上執行超過 50ms的 JavaScript 任務，就被定義為 Long Task。**
    
    ### **為什麼重要？**
    
    當一個任務執行超過 50ms 時，主線程就會被「鎖死」。此時如果使用者點擊按鈕、滾動頁面，瀏覽器完全無法回應，網頁就會出現短暫的凍結、卡死、毫無反應。這也是導致前面提到的 INP 指標超標的最主要元兇。
    
    ### **如何優化？**
    
    - **任務拆分（Task Chunking）：** 將一個需要執行 200ms 的大函式，拆解成 4 個小任務，並利用 setTimeout(..., 0) 或現代的 scheduler.yield() 將控制權短暫還給瀏覽器，讓瀏覽器有機會插隊去處理使用者的點擊或渲染。
    - **使用 Web Workers：** 將與 UI 無關的大量數據運算、加密、解壓縮等複雜邏輯，移到背景的 Web Worker 線程執行，絕不佔用主線程。
    - **防抖與節流（Debounce / Throttle）：** 限制高頻率事件（如滾動 scroll、輸入 input、滑鼠移動 mousemove）觸發 JavaScript 的次數。
    
    ---
    

# **三、 前端四大改進重點**

1. **JavaScript 高效執行**
    - **拆分長任務：**使用 scheduler.yield() 或 setTimeout 釋放主線程。
    - **非干擾性腳本：**延遲載入非必要的第三方追蹤碼，避免初始化阻塞。
    - **被動監聽器：**確保滾動與觸控事件標註為 { passive: true }。
    - **控制 Hydration：**使用漸進式水合 (Progressive Hydration) 減少網頁「僵屍時間」。
    
    ---
    
2. **語意化 HTML：AI 代理的「眼睛」**
    
    如果網頁結構混亂，AI 就無法準確判斷按鈕、輸入框與導覽位置。
    
    - **拒絕 Div 派**：優先使用 `<button>` 而非 `<div onclick="...">`。
    - **標籤補齊**：確實使用 `<label>` 與 `aria-label`。
    - **區域定義**：結構清晰的 `<main>`、`<nav>` 與 `<header>`。
    
    ---
    
3. **無障礙 (ARIA) 即 AI 友善**
    - **鍵盤導覽**：確保網站 Tab Index 邏輯正確。
    - **動態回饋**：狀態變化（如載入中、錯誤提示）須透過 `aria-live` 告知代理。
    - **A11y 分數**：PageSpeed 中的 Accessibility 分數直接等同於「AI 操作親和力」。
    
    ---
    
4. **佈局穩定性：防止「誤點」**
    - CLS 優化：防止累積佈局位移，避免 AI 代理在自動點擊時因畫面跳動而點錯。
    - 預留空間：使用 Skeleton 骨架屏 預留非同步內容空間。
    - 比例固定：圖片與影片必須指定 aspect-ratio。
    
    ---
    

# **四、 傳統 SEO vs. 代理瀏覽優化**

| 優化面向 | 傳統SEO | 代理瀏覽 (AI-Friendly) |
| --- | --- | --- |
| 主要媒介 | 搜尋引擎爬蟲 (Googlebot) | AI 代理 / 瀏覽助理 (Agents) |
| 關注重點 | 關鍵字、Meta、內文 | 互動性 (INP)、DOM 結構、ARIA |
| 互動行為 | 靜態內容擷取 | 點擊、輸入、跨頁任務執行 |
| 成功指標 | 搜尋排名 (Ranking) | 任務完成率 (Success Rate) |
